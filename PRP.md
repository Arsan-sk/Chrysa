# CHRYSA — MASTER WEBSITE REDESIGN PRP

## Product Requirements + Design Specification + Interaction Specification + Implementation Direction

---

# 0. EXECUTION DIRECTIVE

You are designing and implementing the complete website experience for **CHRYSA**, a digital transformation, technology, design, AI, and digital services agency.

This is **not** a generic agency landing page.

Do not approach this as:

> Hero → Services → Projects → About → Contact.

The website must function as an **interactive demonstration of transformation**.

The visitor should progressively move through:

> **Encounter → Recognition → Possibility → Demonstration → Proof → Exploration → Trust → Action**

The website should make a business owner gradually realize:

> **“My business is already working, but it could become significantly more capable than it is today.”**

The final emotional outcome should not primarily be:

> “I need a website.”

It should be:

> **“There is a better version of my business that I haven't built yet.”**

And eventually:

> **“I want to see what Chrysa could build for me.”**

Do not make the website feel like a sales funnel.

Do not aggressively force contact.

Do not hide major website content behind a contact CTA.

Instead, create a progressively more convincing experience where the visitor naturally reaches the conclusion that contacting Chrysa is worth doing.

# 1. BRAND CONTEXT

## 1.1 Brand name

**CHRYSA**

The name is rooted in **“chrysalis”**, representing the stage in which something transforms into something new.

The name should not be represented through literal butterfly imagery.

Avoid:

* butterfly clip art
* obvious butterfly logos
* literal cocoon illustrations
* generic metamorphosis stock graphics
* overly decorative “luxury” symbolism

Instead, interpret transformation abstractly through:

* geometric transformation
* folding
* emergence
* connection
* fragmentation → assembly
* rigid → fluid
* disconnected → connected
* static → responsive
* idea → system
* today → becoming

The visual metaphor must remain sophisticated and abstract.

# 9. TYPOGRAPHY

Typography is one of the primary visual components.

Do not treat typography as merely text content.

Large type should sometimes become:

* an object
* a transition
* a spatial element
* a masking layer
* a scroll-controlled component
* a reveal mechanism
* a visual divider

## Display typography

Use a contemporary, highly legible grotesk/neo-grotesk or similarly modern sans-serif.

Requirements:

* strong large-scale rendering
* multiple weights
* excellent uppercase
* excellent lowercase
* compact display tracking
* strong variable-font support where possible
* high legibility
* confident rather than decorative character

Avoid decorative serif typography as the primary identity.

Avoid luxury-style italic display fonts.

## Body/UI typography

Use a clean neutral sans-serif.

Prioritize:

* readability
* compactness
* comfortable line height
* strong UI clarity

Typography hierarchy must be clearly defined:

* display
* headline
* subheadline
* body
* caption
* metadata
* navigation
* labels
* CTA

# 12. CORNER LANGUAGE

Keep the corner language restrained.

Do not:

* round every component heavily
* use giant pill shapes everywhere
* use SaaS-style floating cards everywhere
* use excessive glassmorphism

Preferred:

* mostly square/subtly rounded structural elements
* modest rounding on interactive/media surfaces
* larger radius only when softness is conceptually useful

The website should feel precise before it feels soft.

Organic transformation should primarily come from **motion**, not from making every object bubbly.

---

# 13. BORDER LANGUAGE

Use thin borders strategically.

Borders may become animated objects.

A border can:

* extend
* retract
* become a connection
* transform into an SVG path
* connect two elements
* animate into a diagram
* act as a progress indicator

This creates a consistent visual relationship between UI structure and system visualization.

# 52. GSAP RESPONSIBILITY

Use GSAP primarily for:

* complex timelines
* ScrollTrigger
* pinned sections
* scrubbed animations
* coordinated transforms
* SVG path animations
* magnetic interactions
* large transitions

Do not use GSAP merely to animate a simple opacity change that CSS can handle.

---

# 53. FRAMER MOTION RESPONSIBILITY

If the architecture uses React/Next.js, Framer Motion may be used for:

* component-level state transitions
* layout transitions
* UI interaction
* presence animations

Do not introduce both GSAP and Framer Motion for the same animation unless there is a clear reason.

Avoid competing animation ownership.

---

# 54. SVG RESPONSIBILITY

Use SVG for:

* paths
* systems
* lines
* diagrams
* transformations
* masks
* geometric interactions
* elastic interactions

Prefer SVG over WebGL when the visual is fundamentally 2D.

---

# 55. THREE.JS / WEBGL RESPONSIBILITY

Use only for:

* spatial transformation
* genuine 3D
* complex shader effects
* immersive system visualization
* technically meaningful hero/section environments

Do not use WebGL merely because it looks impressive.

If a 2D/SVG implementation provides the same conceptual value with significantly better performance:

> **Use 2D/SVG.**

# 56. MOBILE DESIGN

Mobile must be designed intentionally.

Do not simply shrink desktop.

For every interaction define:

### Desktop

What happens with mouse and large viewport?

### Mobile

What happens with touch and small viewport?

### Reduced motion

What happens when motion is disabled?

### Low-performance device

What happens if heavy rendering is unsuitable?

# 57. MOBILE INTERACTION EXAMPLES

> project image follows cursor.

Mobile:

> tap to activate preview.

Desktop magnetic button:

> pointer attraction.

Mobile:

> touch feedback + controlled movement.

Desktop horizontal drag:

> mouse drag.

Mobile:

> native horizontal swipe.

Desktop cursor-driven SVG:

> pointer position controls deformation.

Mobile:

> touch position or scroll progress controls deformation.

Do not force desktop hover behavior onto mobile.

# 59. REDUCED MOTION

`prefers-reduced-motion`

* hidden content
* unusable navigation
* incomplete transformations

Instead:

# 60. PERFORMANCE

Performance is part of the design.

Requirements:

* lazy-load noncritical media
* responsive image sizing
* modern image formats
* avoid unnecessary continuous render loops
* dispose Three.js/WebGL resources
* kill GSAP contexts/listeners appropriately
* animate transform/opacity where possible
* use IntersectionObserver for simple reveals
* avoid excessive DOM nesting
* reduce animation complexity on mobile
* avoid loading massive assets above the fold

The site must feel fast before it feels impressive.
